5. ENDPOINTS DEL API (EXPRESS EN RAILWAY)
================================================================================

Salud:
  GET  /api/health          → { ok, dbReady, uptimeSeconds }

Auth:
  POST /api/login           → { success, token }

Catálogo (optimizado — sin base64 en listado):
  GET  /api/products        → Lista; sanitiza imágenes data:; Cache-Control 60s
  GET  /api/products/:id    → Un producto
  POST /api/products
  PUT  /api/products/:id    → También PUT /api/products con { id } en body (compat)
  DELETE /api/products/:id

Imágenes:
  POST /api/upload          → Sube imagen (Blob o colección media en Mongo)
  GET  /api/media/:mediaId  → Sirve imagen almacenada en Mongo

Banners:
  GET/POST/PUT/DELETE /api/banners

Pedidos:
  GET/POST /api/orders
  PUT /api/orders/:id       → status, items, customerInfo, total

Notificaciones:
  GET  /api/notifications
  PUT  /api/notifications/:id/read

Ticket / factura:
  GET/PUT /api/ticket-config

Socket.io en servidor para nuevos pedidos (panel admin).

6. CRONOLOGÍA DE PROBLEMAS Y SOLUCIONES
================================================================================

--- 6.1 Productos no cargaban / panel vacío ---
Síntomas: Esqueletos grises infinitos; 0 productos; pedidos no en admin.
Causas múltiples:
  a) Frontend apuntaba a API antigua (Vercel: xiaomi-cartagena.vercel.app).
  b) Errores MIME: index-*.js devolvía HTML (faltaba .htaccess en dist).
  c) Backend cPanel con dbReady: false (Mongo bloqueado).
  d) Payload /api/products enorme (~770 KB, ~10 s) por imágenes base64 en Mongo.
Solución:
  - api-base.ts → Railway en producción.
  - public/.htaccess → SPA + excluir /assets y /api.
  - Backend principal en Railway.
  - Sanitizar GET /products (quitar data:image); gzip; caché cliente; stale-while-revalidate.

--- 6.2 Login admin colgado o timeout ---
Causa: API incorrecta o servidor sin DB.
Solución: fetchWithTimeout 10s en LoginPage; mensaje si AbortError; login en Railway con Mongo.

--- 6.3 Edición de productos e imágenes no guardaban / "no se suben" ---
Causas:
  a) PUT /api/products con id en body; Express solo tenía PUT /api/products/:id.
  b) No existía POST /api/upload en Express (solo en Vercel).
  c) Fallback guardaba base64 en Mongo si fallaba upload.
Solución (commit d35eac1d):
  - /api/upload y /api/media en Express.
  - Frontend PUT/DELETE con id en URL.
  - product-image.ts: compresión ~350 KB + error claro, sin base64 en producto.
  - AdminPanel: estados Guardando/Comprimiendo; usar product.id al editar.
  - Servidor rechaza guardar productos con image data: en POST/PUT.

--- 6.4 Rendimiento tienda lenta ---
Medición: GET /api/products ~10 s, ~770 KB (un producto Redmi 15C con PNG base64 741 KB).
Solución (commit 73ace5db):
  - Servidor: sanitizeImageUrl, compression middleware, Cache-Control.
  - Cliente: readProductsCache al iniciar; loading solo si no hay caché;
    catalog-cache.ts; HomePage/CategoryPage skeleton solo sin productos.

Pendiente operativo: Re-subir foto del producto "Redmi 15C + Obsequio" desde admin
(su imagen quedó vacía en listado tras quitar base64).

--- 6.5 Asistente IA bloqueaba clics en móvil ---
Síntoma: Burbuja ancha "¿Te ayudo a elegir tu Xiaomi?" tapaba botones.
Solución (commit 9e7c0778):
  - pointer-events-none en contenedor; auto solo en botones.
  - Móvil: solo FABs compactos (WhatsApp + KG); burbuja larga solo desktop.
  - Teaser corto en móvil primera visita (8 s, localStorage).
  - Chat casi pantalla completa en móvil; safe-area insets.

--- 6.6 Estadísticas en panel admin ---
StatisticsDashboard.tsx: KPIs, gráficas Recharts, filtros 7d/30d/90d/365d/all/custom.

--- 6.7 Migración histórica base64 (antes de Railway) ---
10 productos tenían imágenes base64 en Mongo (>5 MB total); Vercel limitaba 4.5 MB.
Se hizo backup products-backup-base64.json y reemplazo por URLs CDN ligeras.
REGLA: No volver a guardar imágenes en base64 en documentos de producto.

7. DESPLIEGUE — PASOS PARA ACTUALIZAR PRODUCCIÓN
================================================================================

A) BACKEND (Railway) — automático si repo conectado a GitHub
   1. git add / commit / git push origin master
   2. Railway redeploy en 2–5 min
   3. Verificar: https://xiaomictg-production.up.railway.app/api/health
      → dbReady: true

B) FRONTEND (cPanel BanaHosting) — MANUAL cada vez que cambie React
   1. En PC del proyecto: npm run build
   2. Subir TODO el contenido de /dist a public_html del dominio
      (incluye index.html, assets/, .htaccess)
   3. Probar en incógnito: https://www.xiaomicartagena.com/
   4. Si ves JS roto: Ctrl+F5 o vaciar caché; confirmar .htaccess en servidor

C) Compilar servidor localmente (si Railway no compila):
   npx esbuild server/index.ts --outfile=server/index.js --platform=node --format=esm --packages=external

Scripts npm:
   npm run dev     → Vite dev (frontend; API proxy local si configurado)
   npm run build   → Genera dist/
   npm start       → node server/index.js (backend)
